## Planos e equivalência

[Benchmark reproduzível](db02-benchmark.mjs) extrai o SQL de `lastRecordedTs` e o
DDL real das migrations 0005/0013 (todos os seis índices existentes de trades).
Executa o [SQL concorrente](../../ops/sql/db02-trades-last-recorded-index.sql)
literalmente fora de transação. [JSON observado](db02-benchmark-result.json), coleta
iniciada **03:01:08.727 UTC**, contém binds, planos estimados/ANALYZE, amostras e WAL.

100.000 linhas por variante; 1.000 mercados (um com 50.000, demais dividem 50.000),
75% data_api / 25% ws, IDs de mercado 66 caracteres, tokens 77, idades de ~69 dias,
NULL a cada 101 linhas e timestamps futuros a cada 997 linhas elegíveis. Baseline
e candidato em schemas próprios na mesma conexão, sem alterar planner para forçar
índice nem VACUUM para fabricar index-only sem heap. EXPLAIN precedeu ANALYZE;
3 warmups + 20 medições cliente/cenário/variante, cache quente.

| Mercado (sufixo do bind hexadecimal) | Linhas scan antes → depois | Buffers antes → depois | p95 cliente ms antes → depois |
|---|---:|---:|---:|
| Quente (`0`, 50.000 trades) | 100.000 → 1 | 3.125 → 4 | 14,708 → 1,880 |

Linhas scan incluem removidas por filtro/recheck × loops; buffers são os do nó raiz,
sem somar novamente filhos. São medidas sintéticas, não p95/p99 de produção.

## Escrita, espaço e limitação do gate

10.000 inserts novos e 10.000 conflitos **por variante**, em 20 transações de 500
linhas/fase, alternando ordem A/B. Foram exatamente 10.000/0 inserts e 0/10.000
conflitos, sem erros/perdas; os 110.000 registros finais de cada variante têm todos
os campos persistidos iguais (exceto ID gerado). Os schemas foram removidos.

| Medida | Sem candidato | Com candidato |
|---|---:|---:|
| Inserts: tempo ativo / throughput | 727,068 ms / 13.753,88 linhas/s | 726,446 ms / 13.765,64 linhas/s |
| Inserts: p95 COMMIT (20 amostras) | 3,790 ms | 2,812 ms |
| Inserts: WAL de statements | 11.964.901 B | 14.957.869 B |
| Conflitos: tempo ativo / throughput | 109,576 ms / 91.260,82 tentativas/s | 112,212 ms / 89.117,26 tentativas/s |
| Conflitos: p95 COMMIT (20 amostras) | 1,019 ms | 2,789 ms |
| Conflitos: WAL de statements | 29.997 B | 29.997 B |

WAL medido por `EXPLAIN (ANALYZE, BUFFERS, WAL)` de cada INSERT, **0 FPI**; exclui
commit, build e limpeza. Custo marginal de INSERT **+2.992.968 B (~25,01%)**.
Throughput: inserts +0,086%; conflitos −2,349%. P95 COMMIT de conflitos
**+173,56% / +1,769 ms**: **gate ≤10% não atingido**. Não repetir só para selecionar
resultado favorável nem extrapolar essa triagem ao recorder, que insere linha a
linha. DB-04 deve medir o workload real, latência de commits e escrita concorrente
antes da promoção. A amostra não atribui causalidade isolada à regressão de commit.

Índice candidato: **7.847.936 B** após construção concorrente de **527,037 ms**,
**11.747.328 B** após 10.000 inserts. Índices totais: 48.619.520 → 56.467.456 B
antes da escrita; heap igual, 25.600.000 B. Após escrita: índices 55.353.344 versus
67.100.672 B; heap igual, 28.164.096 B. Não extrapolar linearmente a produção:
distribuição, chaves, splits, WAL e espaço de build precisam do orçamento DB-04.

Uma primeira tentativa de carga em INSERT único de 100.000 excedeu 5 s (57014);
schemas foram limpos. A carga foi corrigida para lotes de 5.000, **sem elevar
timeout**; só a execução completa posterior fundamenta as métricas publicadas.
